# Deployment Overview

ObjectOS supports three practical deployment models. Choose based on how
the customer wants to receive artifacts, where data must live, and how
strict the network boundary is.

| Model | Best for | Artifact source | Database |
|---|---|---|---|
| Docker / Compose | Evaluation, PoC, single server, small private deployments | Local file | Artifact datasource or local runtime default |
| Kubernetes | Enterprise production, HA ingress, managed secrets, managed database | Control plane or mounted artifact | Per-project managed database |
| Air-gapped | Customer site, private network, no public internet | Local file shipped with release bundle | Customer-managed database |

## Deployment boundary

ObjectOS is safe to place in a customer network because it is a runtime
boundary, not a builder boundary.

In cloud-connected mode it calls:

```text
ObjectOS -> Artifact API -> Control Plane
```

It does not need to connect directly to the control-plane database.

In file-backed mode it reads:

```text
/artifacts/objectstack.json
```

and uses the runtime/database configuration embedded in the artifact or
provided by the host.

## What to decide before deployment

Before installing ObjectOS, decide:

1. How artifacts are delivered: control-plane API, mounted file, or image
   bundle.
2. Where business data is stored: SQLite for evaluation, or a managed
   PostgreSQL/Turso/MongoDB-compatible deployment for production.
3. How users authenticate: local email/password, OAuth, OIDC/SSO, or
   platform SSO.
4. Where secrets live: environment variables, Kubernetes Secrets, or the
   customer's secret manager.
5. Which optional services the application requires: audit, storage,
   jobs, queue, realtime, automation, analytics, AI, or settings.

## Recommended path

- Start with [Docker](/docs/deploy/docker) for a quick validation.
- Use [Kubernetes](/docs/deploy/kubernetes) for production.
- Use [Air-gapped deployment](/docs/deploy/air-gapped) when the customer
  cannot call a hosted control plane.
